当 Agent 已经能够回答问题、调用工具，下一步往往是把结果变成可以操作的界面：一组可筛选的资讯、一张行情图、一份待填写的表单，或者一个随对话更新的数据看板。

生成式 UI 要解决的，就是从自然语言意图到交互界面这一段。但“让模型生成界面”可以有很不一样的实现方式。模型可以直接写 HTML，也可以只描述组件和数据，再由客户端负责渲染。两种做法在原型里都能跑通，进入产品后，维护成本和权限边界却相差很大。

这次整理以 OpenUI、A2UI 和 json-render 为例，结合四类场景的 Demo 报告，讨论三种路线适合解决什么问题，以及选型时容易混淆的几个判断。

> 本文场景数据与截图来自 2026 年 9 月 26 日的对比报告，截图展示的是用于比较技术路线的自建 Demo，并非三个官方产品的完整评测。原报告记录了 177 项断言，但本文未取得对应源码、模型调用记录和测试日志，因此不把这些数字作为官方框架性能或真实模型成本的证明。框架能力另参考文末官方项目资料。截图中的资讯、证券名称和数值仅用于界面演示，不代表实时数据。

## 一、先看模型到底输出什么

比较这三者，首先要意识到：它们并不处于完全相同的层级。OpenUI 是一个界面生成应用；A2UI 是声明式 UI 标准及相关实现；json-render 则提供把受约束的 UI 描述接入应用的框架能力。

| 路线 | 模型的主要输出 | 客户端的主要职责 | 工程关注点 |
| --- | --- | --- | --- |
| OpenUI 所代表的代码生成 | HTML、样式及可能的脚本 | 预览、隔离并承载生成内容 | 生成代码的执行边界 |
| A2UI 所代表的协议描述 | 组件、数据模型及更新消息 | 将协议映射到受信任组件 | 协议兼容与多端一致性 |
| json-render 所代表的 Schema 约束 | 符合组件目录约定的 JSON | 校验描述并映射到组件实现 | 组件契约与应用集成 |

### OpenUI：把界面表达的自由度交给模型

W&B 的 OpenUI 支持用自然语言描述 UI，并预览、修改生成结果，也提供将 HTML 转为 React、Svelte、Web Components 等形式的能力。本文的 OpenUI 路线 Demo 将生成的 HTML 放进 iframe 中展示。[项目说明](https://github.com/wandb/openui)

这条路线的吸引力很直接：模型可以一起安排布局、样式和 SVG 图形，不必先等待团队把所有视觉元素封装成业务组件。探索页面形态时，这种自由度很有用。

代价是需要认真处理生成代码。iframe 能否隔离风险，取决于 sandbox 配置、脚本与网络权限、消息通道以及宿主如何接收事件。不能只因为用了 iframe，就把生成内容当成可信应用代码。

### A2UI：让 Agent 描述界面，由客户端决定怎么实现

A2UI 将界面结构与具体实现分开。Agent 输出声明式描述，客户端通过预先批准的组件目录，把它映射到自己的界面组件；协议还支持数据模型和增量更新。[项目说明](https://github.com/a2ui-project/a2ui)

这样的分工适合多端产品：同一个业务意图可以交给不同客户端实现，而按钮的外观、表单的交互和组件的可访问性，仍由产品自己的组件体系负责。

但跨端描述并不自动带来跨端一致性。各端是否支持相同组件、属性和事件，仍要通过版本约定和兼容测试保证。声明式输入减少了直接执行模型生成代码的需要，也不会替代后端鉴权或业务权限控制。

### json-render：围绕组件目录建立生成与渲染契约

json-render 的核心思路是先定义 Catalog，再把组件描述映射到 Registry 中的实现，最后由 Renderer 渲染。Schema 可以约束属性形状，框架也支持随着模型响应逐步显示内容。[项目说明](https://github.com/vercel-labs/json-render)

这对已有组件库的团队很有吸引力：模型负责选择、组合组件并填写数据，开发者继续维护组件实现和动作处理逻辑。

原报告把它概括为“只能用于 React、不能跨平台”，这个判断需要修正。官方仓库已经列出 Vue、Svelte、Solid 和 React Native 等渲染器。具体接入成本应按目标端核对，不能把某个 React Demo 的实现范围当作整个项目的边界。

## 二、资讯列表：都能完成，组件数量却不能直接比较

第一个场景是“生成一个资讯列表页”，包含分类筛选、新闻卡片、时间戳和来源标签。三套 Demo 都给出了列表界面。

![OpenUI 路线 Demo 的资讯列表](/images/posts/generative-ui-comparison/openui-news.png)

*OpenUI 路线：以 HTML 和样式组织资讯卡片。*

![A2UI 路线 Demo 的资讯列表](/images/posts/generative-ui-comparison/a2ui-news.png)

*A2UI 路线：把列表拆解为声明式组件及其数据。*

![json-render 路线 Demo 的资讯列表](/images/posts/generative-ui-comparison/json-render-news.png)

*json-render 路线：通过组件描述构建资讯列表。图片可在新标签页打开查看细节。*

原报告记录，A2UI Demo 使用了 66 个组件实例，而 json-render Demo 使用了 9 个顶层组件。看起来后者明显更少，但这两个数字的统计层级不同：顶层组件里面还可能嵌套其他组件，不能直接据此判断哪个框架更简洁。

组件目录的设计也会改变结果。同样是一条新闻，可以拆成 Card、Text、Tag 和 Button，也可以封装为一个 NewsCard。后者通常能缩短描述，却要求客户端先实现专用组件。

因此，这个场景更值得关注的问题是：**团队希望模型组合到多细的粒度？** 通用组件更灵活，业务组件能减少重复描述，也更容易统一交互。组件粒度应由业务变化频率和复用需求决定。

## 三、行情图：差异首先来自组件目录

第二个场景是“生成一个行情分时图”。OpenUI 路线 Demo 展示了 SVG 折线和填充区域；另外两个 Demo 主要用进度条、价格信息和列表表达行情数据。

![OpenUI 路线 Demo 的行情分时图](/images/posts/generative-ui-comparison/openui-market.png)

*代码生成路线直接绘制了折线图。*

![A2UI 路线 Demo 的行情展示](/images/posts/generative-ui-comparison/a2ui-market.png)

*A2UI Demo 使用当前目录中的组件表达价格与区间。*

![json-render 路线 Demo 的行情展示](/images/posts/generative-ui-comparison/json-render-market.png)

*json-render Demo 同样受到本次组件目录的限制。*

这组截图说明，自由生成 HTML/SVG 在探索视觉表达时更方便。但它不能证明 A2UI 或 json-render 不支持图表。准确的结论是：**本次声明式 Demo 的 Catalog 没有提供满足需求的图表组件。**

如果给组件目录增加一个受控的行情图组件，模型就只需要提供序列、时间范围和展示选项。坐标轴、缩放、触控、空数据状态和性能优化，则由图表组件负责。

例如，可以设计这样一份业务组件契约。下面只是概念示例，不是任何框架的协议原文：

```json
{
  "component": "IntradayChart",
  "props": {
    "symbol": "DEMO",
    "series": [
      { "time": "09:30", "value": 100.0 },
      { "time": "09:31", "value": 100.4 }
    ],
    "showVolume": false
  }
}
```

原型阶段可以让模型直接生成图形，以便尽快确定需要什么。进入持续维护的产品后，把确认过的图表能力封装成组件，再让模型生成数据和组合关系，是另一种合理的推进方式。

## 四、输出体积有参考价值，Token 排名需要重新测量

原报告覆盖了资讯列表、行情分时图、登录表单和数据仪表盘四类场景。不过，前文摘要与后文指标表的 KB 数字并不一致。这里仅列出“核心指标对比”表中的字符数，作为该报告记录的样本，不将其换算为字节数或真实 Token 消耗。

| 场景 | OpenUI Demo | A2UI Demo | json-render Demo |
| --- | ---: | ---: | ---: |
| 资讯列表 | 4,809 | 5,577 | 7,960 |
| 行情分时图 | 7,318 | 2,672 | 3,532 |
| 登录表单 | 2,943 | 1,019 | 1,780 |
| 数据仪表盘 | 5,528 | 1,898 | 3,200 |

单位：字符。数据来自原报告，未使用原始响应重新计算。

这批样本可以帮助提出一个待验证的判断：对于内容较多的列表，直接 HTML 描述可能比较紧凑；对于已有组件可以承载的表单和看板，结构化描述可能更短。但行情场景中的视觉能力并不等价，不能用更短的输出证明效率更高。

原报告中的 Token 表还存在算术问题：json-render 三项分别是 2,274、187 和 280，相加为 **2,741**，并非表中列出的 3,461。因此，原来的总量排名、节省比例和成本推算都不宜继续沿用。即使修正加总，不同场景的估算方式也需要先统一。

真正比较成本时，至少应统一模型、输入内容、组件目录和输出要求，并记录模型接口返回的 usage。输入提示词、Schema、失败重试和修复轮次也要计入总成本，不能只比较一次成功响应的输出长度。

响应时间同样如此。报告记录了约 0.4～2.9 ms 的 Demo API 平均耗时，但没有给出模型请求的计时边界。它可以是本地接口处理时间，不能直接当成大模型生成完整界面的耗时。首个可见内容、完整生成和最终可交互，应分别测量。

## 五、安全边界最终要落到组件与动作上

代码生成路线和声明式路线的主要区别，是模型可以控制多大的执行范围。

代码生成路线需要限制生成内容能运行什么脚本、访问什么资源，以及如何与宿主通信。声明式路线将自由度收敛到预定义组件和动作，但开发者仍需保证这些能力本身可靠。

一个 JSON 即使通过 Schema 校验，也可能引用了不应该访问的业务对象。一个按钮即使来自受信任组件库，也不能凭前端传来的参数就执行敏感操作。Schema 检查的是数据形状，业务授权仍应由服务端完成。

落地时，我会把检查分成三个问题：组件与属性是否在允许范围内，动作是否经过宿主明确映射，以及执行动作的用户是否具有对应权限。它们分别涉及渲染约束、应用逻辑和业务授权，缺少任何一层都不能仅靠“声明式”补齐。

## 六、工程选型：从现有产品约束出发

如果目标是探索视觉方案、快速做一个可演示的页面，我会优先考虑 OpenUI 所代表的代码生成路线。它能较快地尝试不同布局和图形，再由开发者评估哪些结果值得进入正式实现。

如果产品需要多个 Agent 向不同客户端返回 UI，团队又愿意投入组件映射与协议兼容工作，A2UI 值得重点评估。此时最关键的是组件目录、数据更新和动作回传能否在目标端保持一致。

如果已有 Web 组件体系，希望在应用里加入动态表单、卡片和渐进式展示，json-render 是值得验证的候选。原有组件能复用多少、生成失败如何回退、状态怎样接入应用，通常比项目热度更能决定接入成本。

| 当前需求 | 优先验证的方向 | 需要先回答的问题 |
| --- | --- | --- |
| 视觉探索与快速原型 | 代码生成 | 生成代码如何隔离和接管维护？ |
| 多 Agent、多客户端的 UI 描述 | A2UI | 目标端能否实现一致的组件契约？ |
| 基于既有组件库添加生成式界面 | json-render | 状态、动作和流式更新如何接入？ |
| 复杂图表与稳定交互 | 声明式路线加业务组件 | 图表能力和数据权限由谁维护？ |

这里没有一个脱离场景的总冠军。团队已有的设计系统、目标平台和业务动作，决定了哪条路线更容易持续维护。

## 七、下一步应该怎样验证

下一轮比较应固定组件目录版本、模型参数和任务要求，把同一份业务数据交给三条路线，检查它们能否完成相同的展示与交互。除了成功样本，还要记录未知组件、缺失字段、超长内容、模型中断和动作失败时的表现。

对资讯列表，要比较筛选和跳转是否真的可用；对行情图，要比较数据点、坐标轴和交互是否等价；对登录表单，要检查校验、提交和错误反馈；对仪表盘，要观察数据更新是否破坏已有状态。最后再结合模型 usage、端到端时间和人工修复量讨论成本。

生成式 UI 的工程价值，在于让产品能够按用户当下的任务组织界面。模型负责到哪一层、客户端保留哪些控制，以及生成失败后如何恢复，这些边界确定之后，框架选择才有具体的评判标准。
